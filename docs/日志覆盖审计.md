# 测试版日志覆盖审计

审计日期：2026-10-23（Asia/Shanghai）。版本：0.1.0-beta.1。

结论：**已有可用的本地日志基础，但功能覆盖不完整；目前仅靠测试者导出的诊断日志，不能还原完整故障过程。** 最优先补齐常驻保护的隔断/恢复历史、功能入口的失败记录、时区流程和前端异常。

本次检查基于当前工作区（含尚未提交的重做代码）、全部 22 个 Tauri 命令、前端现用入口、管理员 helper、watchdog 和本机已有日志。没有执行 DNS/时区修改、防火墙加载、真实断流或发布操作。下文保留首次审计结果，整改情况见下一节。

## 审计后整改（2026-10-23）

以下覆盖表和发现保留为整改前快照。当前代码已补齐：

- 业务操作覆盖验证、执行和保存阶段的最终结果；开始/结束使用随机操作 ID 配对，取消或中断留下 interrupted。手动、启动、设置、后台和操作后检测分别记录。
- 三端 helper 使用管理员拥有的独立日志目录与同一事件格式；进程启动、系统命令错误/恢复、服务安装/停止、watchdog 隔断、重装和自动恢复写入轮转历史。App 和 helper 的原生请求共享操作 ID；旧版 macOS helper 协议仍可处理普通操作。
- DNS 预检与恢复、时区手动/跟随/恢复、查询服务与 fallback、设置、工具、报告、浏览器打开和退出均加入日志。频繁检测记录状态变化和受限频率的耗时心跳。
- 前端加入 React 错误边界、全局异常/未处理拒绝、IPC 与事件订阅失败记录；只上报固定事件标识。错误边界内仍可导出日志。
- 日志包合并 App 与系统保护事件，包含每会话版本/平台/架构、可用的构建提交、日志丢弃/读取失败/损坏行计数。系统日志无法收集或不完整会明确标识；Windows/Linux 导出系统日志可能请求授权，取消后仍保存 App 部分。
- panic 记录固定原因码；App 下次启动能识别未正常结束的会话。此能力不能替代 OS 对段错误、强制终止等原生崩溃的诊断。
- App 与系统保护各受限于四份约 512 KiB 文件；同一系统的 helper 进程共享其系统日志目录，通过跨进程文件锁保护轮转。每次写锁最多等待约 30ms，写失败计入健康信息。
- 测试覆盖脱敏、全部轮转、损坏文件、锁竞争、并发操作配对、中断、旧格式兼容和前端上报限频。具体实机断流与权限交互仍按文末清单执行。

打包流程改为仅上传未发布草稿 Release，不上传 Actions 安装包 artifact；不自动公开发布。

## 已有基础与本机证据

- `src-tauri/src/audit.rs` 使用 JSONL，字段为 UTC 时间、会话 ID、操作、结果、错误类别、可选耗时。
- 当前文件加 3 个历史文件，每份约 512 KiB，合计约 2 MiB；按体积轮转，不是按天保留。设置中的 `historyDays` 只清理业务历史，不控制这些日志。
- Unix 日志目录创建为 0700，新日志文件创建为 0600。原始错误只用于映射类别，不写入日志；事件名限制为短的字母、数字、点和下划线组合。
- 设置里的“查看”只取最近 100 条；“导出”带上轮转日志、当前版本、OS 和架构。
- 本机现有 3 个日志文件，共 6,283 条、23 个会话，未发现不能解析的行；文件权限均为 0600。样本时间为北京时间 10 月 22 日 20:50 至 10 月 23 日 13:09。样本可能包含前几次开发构建，仅用于核对现有收集行为。
- 其中 IPv4 探测 `unavailable` 14 次、DNS 探测 `unavailable` 16 次，30 条的 `errorKind` 均为空。有错误类别的 19 条中，17 条只有 `operation_failed`，2 条为 `permission`。
- `cargo test --manifest-path src-tauri/Cargo.toml --locked audit::tests -- --nocapture`：1 个日志测试通过，验证敏感错误内容不落盘、非法事件名被拒绝、一次文件轮转。该测试不验证各功能埋点，也不代表完成三平台实机验收。

业务历史 `state.json`、最新保护状态 `protection.json`、root helper 的状态回执，与诊断日志是不同数据源。业务历史里有中文提示，不等于诊断日志导出里有该功能记录。

## 发布前优先补齐

### 1. 常驻保护事件没有进入可导出的历史（高优先级）

证据：`src-tauri/src/main.rs:16` 的 helper/watchdog 分支在进入 `run()` 前返回；唯一的 `audit::init` 位于 `src-tauri/src/lib.rs:1486`。`src-tauri/src/firewall/watchdog.rs:410` 的恢复、`:430` 的隔断及 `:467` 的 `hold` 只更新状态回执，没有日志埋点。UI 的 `sync_tunnel_status`（`lib.rs:278`）同样没有为状态迁移记录事件。`export_diagnostic_logs` 仅收集 App 的 `audit::entries()`。

影响：用户报告突然断网、自动恢复、helper 循环重启时，导出日志不能给出完整时间线；当前状态后来被刷新后，先前原因可能无法追溯。

建议：root 进程使用自己拥有的受限目录和独立轮转文件，记录受控的事件名与原因码。通过受限接口导出脱敏事件，并与 App 包合并；勿让 root 直接信任用户可修改的日志路径。状态变化时必记，重复健康轮询限频。紧急解除操作也应留记录。

### 2. 功能入口没有完整结果，原生请求成功也不等于功能成功（高优先级）

证据：`lib.rs:327` 到 `:334` 只包住 `firewall::elevated`；准备计划、DNS 预检、用户确认、计划有效期和请求后回读判断均可能在其外失败。`lib.rs:435` 开始记录检查，但 `:438`、`:449` 等早退不会写手动检查错误终态。原生包装层将任意 `Ok(receipt)` 记为 `ok`，其后功能层仍可能因规则未确认而报错。

影响：一次失败操作可能完全没有记录、只有 start，或者留下一条看似成功的原生请求；同样的 `firewall.apply` 也不能区分 IPv6、隔断和全局保护。

建议：统一包住每个业务命令的验证、执行、回读和保存，使用操作 ID 关联开始与结束，加入静态阶段码和策略种类。分别表达“请求返回”和“规则配置已确认”。区分手动、启动、后台、恢复后复查等来源。高频快照只记异常与状态迁移。

### 3. 时区与前端故障难以复现（高优先级）

证据：`lib.rs:944`、`:953`、`:1070`、`:1131` 的手动/跟随/应用/恢复流程没有完整日志；仅 `:1529` 为后台跟随失败补一条事件。`src/main.tsx`、`src/App.tsx`、`src/lib/api.ts` 没有统一前端异常上报及 React 错误边界。

建议：时区记录模式、触发来源、服务枚举、缓存/回退、验证与应用阶段码，成功/失败均覆盖。前端增加 Error Boundary、全局 error/unhandledrejection 与 IPC 初始化失败记录；错误信息通过受控分类处理，防止 URL、路径和 IP 随原始 message/stack 泄漏。原生崩溃至少增加正常退出标记和下次启动的异常结束提示；panic 采集与 OS 原生崩溃诊断应区分能力范围。

### 4. 失败分类过粗（中优先级）

证据：`probes.rs:183` 到 `:195` 只保留状态，固定传 `None` 作为错误和耗时；`audit.rs:111` 只按文本猜测 timeout / permission / invalid_data，其余为 operation_failed。`probes.rs:292` 的时区用出口查询直接调用 `probe_egress`，还会绕开 `run` 中的探测日志循环。

建议：使用确定的原因码，如 `request_timeout`、`http_status`、`connection_or_tls_failed`、`invalid_response`、`proxy_path_required`、`geo_database_missing`、`plan_expired`、`receipt_mismatch`、`admin_cancelled`、`helper_unavailable`；能够可靠识别时再细分 TLS 与代理失败。记录数字 HTTP 状态、耗时、阶段和是否重试，无需保存原始错误、地址或服务响应。

### 5. 日志自身失败会被静默忽略（中优先级）

证据：`audit.rs:132` 忽略写入错误与锁失败；`:95` 附近跳过不可读文件和不能解析的行；`:139` 失败可返回空列表。初始化失败反而会使 App setup 返回错误。

建议：维护日志可写状态、最后失败原因码、丢弃计数；导出时带出文件读取/解析异常摘要。明确初始化失败时的可诊断降级行为。避免磁盘满后用户以为日志仍正常。

### 6. 补足每会话上下文和导出可用性（中优先级）

当前缺少每会话 App 版本/构建标识、系统版本、进程来源、操作关联 ID。导出的版本属于当前程序，不能准确解释同目录内旧构建的事件。持续轮询会消耗约 2 MiB 的日志保留空间；最近 100 条也容易被重复探测占满。

建议：每次会话记构建与运行环境，保留重要状态迁移，健康心跳采样。导出包含可用的 UI、后端和 helper 脱敏事件及日志健康摘要，提供可发现的保存位置。业务历史和诊断文件的保留规则应分别说明。

## 补齐后的验收清单

- 每个修改类操作验证成功、输入拒绝、用户取消授权、原生执行失败、规则回读不匹配、保存失败各至少一次；均有可关联的最终结果。
- 分别验证 TUN 关闭、模式改变、节点改变、DNS 路径改变、控制接口不可用、规则被修改：能还原原因、隔断执行和恢复时间线，UI 关闭后仍有 helper 记录。
- DNS 预检失败、部分恢复；时区查询超时、服务回退、出口变化、权限拒绝、应用成功、恢复成功均有事件。
- 注入可控前端渲染异常和未处理拒绝，确认能在重启后导出；对原生 panic/异常结束单独验收。
- 验证并发操作关联、跨重启、全部四份轮转、不可写目录、损坏行、导出写盘失败，以及旧版本事件识别。
- 在输入/错误中放入测试 IP、节点名、用户路径、token 和订阅 URL，确认日志包不含这些原值。
- Windows、Linux 的权限组件和 helper 收集路径需要各自实机验收，不能仅以 macOS 测试通过代替。
